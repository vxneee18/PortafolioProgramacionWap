1. Configuración de Entorno y Descubrimiento de Red

Fundamento Teórico: La arquitectura de red host-only o Red NAT permite segmentar el tráfico entre máquinas virtuales, simulando un enlace de área local físico. En este segmento, las direcciones IP se resuelven a nivel de capa de enlace (L2) usando el protocolo ARP (Address Resolution Protocol), enviando tramas broadcast para correlacionar direcciones IP lógicas con direcciones físicas MAC.

Aislamiento en VirtualBox

Se implementó un adaptador con topología de Red NAT (nombre: NatNetwork) compartido entre Kali Linux y Snakeoil para permitir enrutamiento controlado y aislamiento de equipos externos.

Descubrimiento de Hosts Activos

Para determinar la asignación dinámica de la máquina de prueba sin interacción en el host objetivo, se ejecutó un barrido mediante arp-scan consultando la tabla ARP del segmento 10.0.2.0/24:

2. Escaneo de Servicios y Puertos

Fundamento Teórico: La técnica TCP SYN Scan (-sS ejecutada bajo sudo) envía paquetes SYN a los puertos de destino sin completar el saludo de tres vías (3-Way Handshake). Si el host responde con SYN/ACK, el puerto se clasifica como abierto; si responde con RST/ACK, se clasifica como cerrado. La detección de versiones interroga las cadenas de texto expuestas por los demonios activos en sus respectivas conexiones.

Comando aplicado para escaneo exhaustivo sobre los 65,535 puertos:

sudo nmap -p- -sV -sC -T4 10.0.2.4 -oN escaneo_snakeoil.txt

3. Enumeración Web y Análisis de Endpoints

Fundamento Teórico: El fuzzing de directorios web envía peticiones HTTP iterativas usando listas de palabras comunes para detectar rutas no indexadas. La evaluación de los códigos de respuesta del servidor (RFC 7231) permite categorizar el comportamiento: 200 OK indica lectura directa, 405 Method Not Allowed señala restricciones en los verbos HTTP (como esperar POST en lugar de GET), y 500 Internal Server Error denota fallas en el procesamiento de lógica backend.

Ejecución de gobuster sobre ambas interfaces HTTP:

gobuster dir -u http://10.0.2.4:8080 -w /usr/share/wordlists/dirb/common.txt -t 30
Figura 3.1: Identificación de endpoints en el puerto 8080, destacando /registration, /login, /users y /secret.

Mapeo de Rutas Clave

  • /registration (Status 200): Interfaz para registrar cuentas de usuario.
  • /login (Status 405 en GET): Endpoint de autenticación que espera envío de parámetros por método POST.
  • /users (Status 200 en GET): Consulta pública de la lista de cuentas en el backend.
  • /secret (Status 500 / 405): Zona restringida que requiere cabeceras de autorización y validación de roles.

4. Interacción con la API e Identificación de Credenciales

Fundamento Teórico: Las APIs REST estructuradas con formato JSON procesan datos en el cuerpo de peticiones POST y manejan estados de autenticación sin sesión mediante tokens JWT (JSON Web Tokens). Estos tokens contienen información de cabecera, payload y una firma criptográfica para garantizar integridad entre cliente y servidor.

Registro y Creación de Sesión

Se envió una petición con carga útil JSON para dar de alta un usuario y validar el formato de respuesta del backend:

curl -i -X POST http://10.0.2.4:8080/registration \
     -H "Content-Type: application/json" \
     -d '{"username":"vane", "password":"Password123"}'
Figura 4.1: Confirmación de cuenta creada y recepción del primer token de acceso JWT.

Al consumir el endpoint /users mediante el método GET, el sistema expuso los identificadores registrados y los valores hash de protección:

curl -i http://10.0.2.4:8080/users

Estructura de la función de derivación de claves expuesta:

$pbkdf2-sha256$29000$e0/J.V.rVSol5HxPqdW6Nw$FZJVgjNJIw99RIiojrT/gn9xRr9SI/RYn.CGF84rO40

5. Análisis del Esquema Criptográfico y Conclusiones de Fase

Fundamento Teórico: PBKDF2 (Password-Based Key Derivation Function 2) aplica una función pseudoaleatoria (en este caso HMAC-SHA256) junto con una sal (salt) a lo largo de un número alto de iteraciones (29,000 en esta instancia). Esto incrementa el costo computacional por intento, dificultando ataques de fuerza bruta masivos sin aceleración de hardware específica.

Se aisló el valor hash para su evaluación con herramientas de procesamiento local:

echo 'patrick:$pbkdf2-sha256$29000$e0/J.V.rVSol5HxPqdW6Nw$FZJVgjNJIw99RIiojrT/gn9xRr9SI/RYn.CGF84rO40' > hash.txt
john --format=pbkdf2-hmac-sha256 --wordlist=/usr/share/wordlists/rockyou.txt hash.txt
Figura 5.1: Registro de tasa de cómputo (~573 c/s) evidenciando el retardo inducido por el factor de trabajo de 29,000 iteraciones.

Hallazgos Principales

  • Exposición de Información Sensible: El endpoint /users carece de controles de autorización (Broken Object Level Authorization), permitiendo a cualquier entidad no autenticada listar nombres de usuario y hashes.
  • Robustez en Almacenamiento: A pesar de la fuga de datos, el uso de 29,000 iteraciones en PBKDF2 previene la resolución trivial mediante diccionarios genéricos sin un ataque altamente enfocado o acceso a diccionarios adaptados.
  • Gestión de Métodos HTTP: Los endpoints del backend aplican restricciones de verbos que exigen transacciones controladas por API para la manipulación de estados de sesión.
